# 后台分组与隐藏图标操作

状态：**0.5.0 开发中，尚未发布。** 本文记录当前实现边界与公开研究依据，不代表所有菜单栏项目已通过验证。当前 macOS 27 路径不模拟鼠标，通过原生排序记录隐藏项目，并允许采集或点击时临时展示单项；菜单关闭后重新隐藏，正常退出时恢复接管前位置。它替代的是旧合成拖动／点击机制，不是否定用户已接受的单项临时显示。不同二进制的实测记录仍保留在[独立图标栏开发与验证记录](ICON-PANEL-VERIFICATION.md)。

## 用户要求与当前实现

在设置中应用分类，以及点击独立图标栏中的隐藏项目，都不得接管系统鼠标或发送全局模拟键鼠事件。隐藏光标、短暂移动后复位、阻止用户输入，都不满足这一要求。后台接口仍可能按用户意图打开目标应用的菜单或窗口；“后台”不表示目标界面永远不获得焦点。

当前实现采用以下路径：

| 操作 | 当前路径 | 成功依据与不支持时的行为 |
| --- | --- | --- |
| 应用列表分类 | macOS 27 对经当前源对象、owner 和现有排序键核对的项目，使用原生位置记录及持久隐藏账本；其他适用路径仍要求 `AXPosition` 可写 | 实际可见位置与隐藏结果须分别验证，不能用权重读回代替。身份、位置或恢复结果不确定时保留草稿／恢复记录，不发送模拟拖动 |
| 获取原始图标及点击隐藏项目 | 必要时通过排序记录临时展示单项，确认真实可见位置后采集原始图像；点击前核对身份和展示基线，再请求一次支持的 AX 动作 | 图像采集与菜单出现分别核验。动作返回成功不作展示证明；未知结果不自动重复动作或补发鼠标点击 |
| 准备系统溢出区 | 仅尝试对应对象的 AX 动作，并读取入口状态 | 无法确认后台展开时提示手动展开后刷新，不停驻、移动或恢复系统指针 |
| 单项调用结束及应用退出 | 目标菜单关闭后将本次临时显示项恢复到隐藏记录；正常退出恢复接管前的原值 | 检查当前值是否仍属于本应用的写入，再恢复并验证；失败保留恢复状态，不覆盖外部修改，也不把目标菜单状态未知当作已关闭 |
| 用户主动拖拽分组 | 用户自己按住 ⌘ 使用 macOS 的原生操作 | 应用只读取稳定位置并保存确认结果；这不是自动分类失败后的合成输入回退 |

草稿持久保存，但不等于原生分类已经生效。已严格绑定的稳定身份可跨启动保存选择；仍只有 session 身份的选择重启后保留为待明确关联草稿，不能按应用名自动套用。点击动作与图像获取也是不同能力：图标快照仍可能缺失或过时；macOS 27 当前使用内存缓存，隐藏期间不会实时更新。数据位置见[用户数据与存储位置](USER-DATA.md)。

## Apple 公开 API 能证明什么

### 辅助功能动作

`AXUIElementCopyActionNames` 返回对象支持的动作，`AXUIElementPerformAction` 向该对象请求执行动作。调用本身不要求本应用移动系统指针。动作支持范围由目标应用决定；返回 `cannotComplete` 也可能只是目标进入了菜单跟踪或其他模态处理，不能直接推断没有执行。因此当前方案保持一次请求，再观察结果，避免自动重复触发。[动作列表](https://developer.apple.com/documentation/applicationservices/1462053-axuielementcopyactionnames)、[执行动作](https://developer.apple.com/documentation/applicationservices/1462091-axuielementperformaction)

`AXPress` 和 `AXShowMenu` 是不同的动作意图，不能假设每个图标都支持，也不能假设原应用对象、宿主镜像对象的动作行为完全一致。macOS 27 的远程菜单栏宿主需要保留原对象身份，并把展示几何与动作身份分开核验。[Apple AX 接口集合](https://developer.apple.com/documentation/applicationservices/axuielement_h)

### 位置属性与自动分类

`AXUIElementIsAttributeSettable` 可以查询指定对象的属性是否可修改；查询成功且可写，才构成尝试 setter 的前提。它不承诺任意菜单栏项目支持重排。Apple SDK 对 `AXPosition` 的说明是通常不可写，用户可直接移动的部分元素可以提供可写位置；因此必须逐个查询，并在写入后验证真实顺序。[属性可写性](https://developer.apple.com/documentation/applicationservices/1459972-axuielementisattributesettable)、[AX 读写接口](https://developer.apple.com/documentation/applicationservices/axuielement_h)

`NSStatusItem` 公开接口管理调用者自己创建的状态项，包括长度、可见性和菜单；它不是任意第三方状态项的统一重排服务。当前不能把修改偏好中的位置提示当成已完成第三方重排。[NSStatusItem](https://developer.apple.com/documentation/appkit/nsstatusitem)

### 进程定向事件的研究边界

`CGEvent.postToPid` 将事件投向指定进程的事件流；其参数没有窗口 ID。公开事件字段 `mouseEventWindowUnderMousePointer` 和 `mouseEventWindowUnderMousePointerThatCanHandleThisEvent` 可以作为研究对象，但字段存在不等于 Apple 承诺用它们可以可靠路由到任意窗口或 macOS 27 的某个远程状态项。[postToPid](https://developer.apple.com/documentation/coregraphics/cgevent/posttopid%28_%3A%29)

`CGEventSource` 的私有状态表用于独立跟踪事件源状态；它不是独立鼠标指针的承诺。进程定向投递仍属于合成事件，必须单独证明目标接收、没有全局投递，以及系统指针不受影响。不能仅因调用名称含 PID 就把它标为符合本项目约束。[CGEventSource](https://developer.apple.com/documentation/coregraphics/cgeventsource)

当前产品没有启用进程定向投递作为回退。自有接收窗口的初步实验见下文；后续仍需按原始对象、宿主进程及真实窗口关联逐项验证，不能从自有窗口结果推断远程菜单栏项目支持。不得同时向多个候选 PID 试投，或在未知结果后自动切换路径重复点击。

## Ice 源码的实际机制

已核对 Ice 上游 `main` 的 `MenuBarItemManager.swift`。它的事件投递封装确有 `postToPid` 分支，但移动的 `scrombleEvent` 会在 owner PID 和 session 事件流之间转发；点击直接使用 session 投递。外围还隐藏光标，并在结束后 warp 回保存位置。因此这套代码不是“纯进程定向、不影响系统指针”的已验证参考。[投递与转发](https://github.com/jordanbaird/Ice/blob/main/Ice/MenuBar/MenuBarItems/MenuBarItemManager.swift#L679)、[移动](https://github.com/jordanbaird/Ice/blob/main/Ice/MenuBar/MenuBarItems/MenuBarItemManager.swift#L998)、[点击](https://github.com/jordanbaird/Ice/blob/main/Ice/MenuBar/MenuBarItems/MenuBarItemManager.swift#L1170)、[光标封装](https://github.com/jordanbaird/Ice/blob/main/Ice/Utilities/MouseCursor.swift#L22)

该实现同时设置目标 PID、事件标记、公开窗口字段 91/92 和私有 raw field `0x33`。源码将 `0x33` 命名为窗口 ID，但仅凭上游源码不能独立证明它是路由成功的决定因素。上游路径也没有证明将同样字段用于 macOS 27 单一菜单栏宿主就能成功。不能把私有字段默认带入产品；如研究，应与公开字段测试明确分开。[字段定义与事件构造](https://github.com/jordanbaird/Ice/blob/main/Ice/MenuBar/MenuBarItems/MenuBarItemManager.swift#L1550)

这里只使用源码事实判断方案，不移植 Ice 的 GPL 实现。公开代码、API 存在、编译通过与实际满足“不接管鼠标”是不同层次的证据。

### 自有窗口的进程定向事件实验

21:42 的签名实验进程中，辅助功能信任和事件投递访问检查均为 `true`。实验共发送 **30 个定向事件**；**901 次系统指针采样未观察到位移**，未观察到全局鼠标按钮状态变化，也未激活应用。事件发送、应用级接收与具体窗口／视图接收分别记录，不能互相替代。

| 事件字段组合 | 应用级接收 | 窗口与视图接收 |

### 远程宿主的定向输入复测

随后继续对本进程的 MT-A、MT-B 两项开展实验，没有向第三方应用图标发送合成事件。为取得真实可见位置，实验为两项创建带本轮 UUID 的独立 autosave 名称，并仅设置自己的位置提示 A=54、B=108。每次结束先移除状态项，再恢复或删除这两个临时偏好键；运行后也核对了持久偏好中没有遗留 `MenuTidyProbe-` 键。位置提示只用于自有试验项，不构成第三方图标重排方案。

已确认 macOS 27 的宿主 AXButton 与系统命中返回的原应用 AXMenuBarItem 可以不是 `CFEqual`。本实验通过本进程 PID、两个允许的明确标识、完全一致的源 frame，以及重新读取的唯一宿主父子链核对镜像。最终两项实际容器分别是 `(1459.5, 0, 54, 33)` 与 `(1405.5, 0, 54, 33)`，都位于 MenuBarAgent 的同一个真实 CG 窗口 22 中。不是按窗口名称或相邻位置猜测目标。

只读私有 `NSSceneStatusItem.hostWindowID` 返回 0；本地虚拟窗口号仍分别为 2³²、2³³。它们不能当成 32 位 CG 窗口号使用。对原应用定向发送时，应用级监视器确实收到事件和原标记，但 `windowNumber = 0`，没有进入图标 action。系统还会重写事件编号，不能仅凭预设的编号认定 scene 转发成功。

最终协议修正实验使用相同的 `mouseEventNumber` 配对一次手势中的 down/drag/up，并设置单调开机时间戳；私有窗口字段仍仅存在于显式诊断模式。安装包 SHA-256：

```text

```

| 实验 | 收到的行为 | 指针与全局按钮观察 | 结论 |

| 向确认的宿主窗口发送一次点击（2 个事件） | A、B action 均为 0 | 269 次采样无位移，无全局按钮按下 | 没有取得点击成功证据 |

### 2026-09-25 身份与草稿恢复边界

只读核查确认，重启 Menu Tidy 后选择丢失有两个独立原因：

- **草稿没有持久化。** `MenuTidyModel.setGroup` 只更新内存中的 `drafts`，启动时直接从已保存的 `rules` 重建草稿。因此尚未应用的选择即使具有稳定 ID，也会在重启后丢失；`persistRules` 还会主动排除全部 `session:` 规则。
- **会话 ID 只能在当前 Menu Tidy 进程中复用。** `MenuItemIdentity` 仅在 bundle identifier、非空 AXIdentifier 和本次扫描唯一性均满足时生成持久键。其他项目由 Access 分配 `session:<pid>:<UUID>`，后续只凭同一源进程启动时间及 `CFEqual` 在内存中复用。Menu Tidy 重启后原 AX 对象表消失，UUID 会重新生成。最新扫描日志的重复键桶为 0，但日志没有逐项记录外部标识，不能仅凭该日志将所有会话项归因于同一种缺失原因。

PID 与启动时间只能识别应用进程，不能识别该进程的具体菜单栏项；一个存活的应用可以同时持有多个项，也可以删除后重建。名称、标题、图像、位置、枚举顺序均不能证明项身份，`CFHash` 也没有无碰撞、跨客户端重启持久的身份契约，不能代替 `CFEqual`。

本次读取的公开 SDK 将 accessibility identifier 声明为可空属性；没有查到可将任意外部 AX 项序列化并在客户端重启后恢复的公开身份接口。源应用的 `NSStatusItem.autosaveName` 可用于它自己的偏好持久化，但没有已验证的公开 AX 关系把外部项对应到该名称。仅枚举源应用的菜单栏偏好键不能完成这种映射。现有源码和日志也未证明可读取并严格关联外部项的 scene identifier。私有 remote token 的存在不等于已有可导出、可持久化且可安全重建任意项的契约，本产品未实现这条路径。

**以下是未实现的建议，不是已经具备的恢复能力：** 先单独持久化草稿及其身份范围；重启后可准确关联的稳定 ID 恢复为待应用，无法解析的会话项保留为待重新关联记录，不自动套用到同名或同进程的新项。这样可以避免选择数据直接消失，但不能承诺会话项自动重新绑定。若以后要求在源应用仍存活期间自动跨 Menu Tidy 界面重启恢复，可评估持续存活的身份代理保留原 AX 引用，再凭进程实例、实际 AX 树和 `CFEqual` 重新验证；代理退出、源项重建或关联不明确时仍须拒绝自动恢复。这需要额外的生命周期与权限设计，当前没有实现。

跨源应用重启的长期恢复仍依赖源应用提供语义稳定且唯一的项目标识，或另一个得到验证的明确关联接口。当前没有通用方法为未提供标识的第三方图标制造这种身份；图像缓存、后台点击成功和宿主几何绑定均不解决这一限制。本节只记录源码与 SDK 核查结果，未修改 Model、执行 AX 探针或验证任何新的恢复能力。
