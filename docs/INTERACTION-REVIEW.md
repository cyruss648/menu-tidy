# 交互与执行流程评审

本轮针对用户提供的「等待后分组失败」截图、当前原生管理窗口和后台执行链进行评审。修改前完整保存工作区为 `cb2c79e`；该快照包含 99 个文件，提交门禁通过。基线完整检查通过 299 项 Swift 和 80 项 Python 测试。这些测试不代表第三方菜单栏操作全部兼容。

## 评审结论

问题主要来自执行流程的耦合，而不只是错误文案。用户想修改分类，却同时承担了读取全量辅助功能树、修复边界、反复临时显示、获取截图及最终验证的成本。普通刷新还可能自动进入写位置流程。系统拒绝、空间不足和身份歧义本应尽早反馈，原实现却可能在大量工作后才发现。

| 优先级 | 发现与证据 | 用户影响 | 本轮处理方向 |
| --- | --- | --- | --- |
| 高 | `applyStagedPositionHidingRules` 在逐项显示与采集后才完成首次批量边界检查；截图错误来自 `fitPositionHidingBlocker` | 已等待多项操作后，整批因为共同前提失败 | 先检查目标身份、宿主与显示器条件；有完整可见证据时，在批量暂存后立即适配真实边界；保持最终验证 |
| 高 | `refreshMenuItems` 成功退出时可能调用 `applyItemRules(onlySavedRules: true)` | 用户只想刷新列表，却触发隐藏与排序写入 | 刷新只读取，重新应用必须显式发起 |
| 高 | 普通应用自动调用 `resolvePositionKey`，逐个尝试候选位置的双向移动 | 歧义项目扩大批量延迟，并改变临时布局 | 普通应用不自动进行写入式位置探测 |
| 高 | 扫描只限制节点数，部分子对象没有逐对象配置 AX 超时 | 无响应应用使读取时间膨胀 | 单次扫描共享 3 秒读取预算；中止时保留上一份列表 |
| 中 | 截图失败会中断分类流程；普通刷新也做图像采集与能力诊断 | 次要功能拖慢或否定主要操作 | 刷新列表、应用分类、更新图像分成独立动作 |
| 中 | 当前窗口显示「本次可应用 18 项」，但实际只知道有 18 条待处理选择 | 让用户误以为已确认这些项目可成功执行 | 明确区分草稿、已保存但待核实的规则与当前选择 |
| 中 | 失败区把阶段、原因、部分成功和底层实现长句连续展示；没有停止入口 | 难以判断下一步，也不能主动结束长任务 | 短摘要、恢复动作、折叠详情、阶段进度与停止后的恢复状态 |

实机进一步发现：隐藏前 divider 的当前位置属于拥挤布局，不能代表目标移入隐藏区之后的可用空间。直接要求该位置能拟合最终边界，会产生假阴性。本轮将「可以准备边界」与「最终空间适配」分开；不预估或伪造未来坐标，适配仍读取实际变化后的原生几何。

逐项预检还解决了批量阻塞：不能唯一匹配排序记录的项目单独跳过，保留其选择并显示原因；其余项目继续执行。中途超时、取消不等于未检查的项目不受支持。已经受管理的隐藏项仍必须完整纳入最终证明，不能为了继续而丢弃原有恢复记录。

## 操作契约

1. **选择显示方式**：立即保留草稿并更新列表；选择本身不等于真实菜单栏已变化。
2. **刷新列表**：只重新发现项目及当前状态，不重新应用保存规则，也不主动逐项显隐来获取图片。
3. **应用分类**：先检查权限、恢复状态、身份对应、宿主和显示器条件，再执行必要改动并适配实际边界；只有真实位置验证通过才提交规则和移除草稿。已处于可见状态的目标直接提供初始证据，避免不必要的隐藏／显示／再隐藏；无需移动的常驻项共享整批最终扫描。
4. **更新图像**：用户显式发起，可逐项临时显示、采集和恢复；图像缺失与分类失败分别反馈。
5. **停止**：停止发起后续工作，等待已经开始的位置改动完成条件恢复；恢复完成前保持互斥，恢复失败保留记录与恢复入口。

不能以设置写入成功替代真实可见性证明，不能以「已停止」掩盖仍在后台执行的写入，也不能为了更快而删除恢复账本。

刷新列表、应用分类与更新图像使用同一套前台操作状态，提供已用时间、阶段与停止入口。单次 AX 扫描共享 3 秒预算，普通刷新前台预算 6 秒，应用为 12–20 秒，图像更新为 30 秒。预算通过单调时钟和工作边界检查执行，并非硬实时完成承诺；系统调用和必要恢复可能增加总用时。恢复使用独立的局部等待预算，不能因为前台任务已过期而直接判定恢复失败。原生拖拽整理的结束流程不包含完整的这套停止／计时交互。
