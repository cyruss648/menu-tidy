# 系统图标托盘验证（2026-09-29）

候选版本 0.6.1，构建 56。代码提交 `2e23fe13b55d466c521f5c4d2d0df928f116854f`，分支 `feature/visibility-ownership-repair`。

[GitHub 签名构建](https://github.com/cyruss648/menu-tidy/actions/runs/36552349502) 的 arm64 与 x86_64 均成功。此工作流只生成签名候选，没有发布正式版本或更新自动更新源。安装使用 arm64 产物，核对归档 SHA-256、Sparkle EdDSA、专用证书、应用标识、版本、构建号、二进制哈希及深度严格代码签名；原安装已备份。

## 用户行为

“收起后隐藏”保留 Menu Tidy 托盘入口。点击系统入口时临时恢复原生图标，重新识别系统创建的新对象，调用其原生辅助功能操作；确认原生菜单或面板关闭后再隐藏。退出 Menu Tidy 时恢复其管理的系统显示入口。隔空投送功能与输入法配置不随图标收纳而关闭。

## 修复

- 输入法切换采用精确系统程序路径、进程生命周期和完整且重复的唯一 AXExtrasMenuBar 子项枚举，不使用显示名称猜测身份。保存规则使用独立命名空间的持久标识，与 AX 标识和排序偏好标识区分。
- 输入菜单的 `visible` 仅接受 Boolean，隔空投送仍只修改已验证的显示位。两项使用独立恢复记录；日志版本 2 保持读取旧版 AirDrop 记录的能力。
- 扫描包含所有连接屏幕。实际双屏布局中第二块屏幕原点为 `(1920,-37)`，旧版只扫描第一块屏幕而漏掉其他屏幕的原始图标。
- 隔空投送在不同屏幕的系统对象可不同。完整宿主枚举之后，只以唯一的系统 extras 原始项驱动托盘，逐屏检查对应项；同屏重复、身份改变和不完整读取仍拒绝处理。
- 外部应用的 AXMenuButton 作为已知叶节点，不再阻断系统宿主枚举。

## 实机结果

环境：Apple Silicon、macOS 27、两块显示器。测试未改变隔空投送接收范围或当前输入法选择。

| 场景 | 结果与证据 |
| --- | --- |
| 隔空投送隐藏与托盘入口 | 系统原生枚举不再包含 AirDrop；托盘仍有“隔空投送”按钮 |
| 点击隔空投送 | 最终构建 56 打开真正的控制中心隔空投送面板；功能开关仍为开启，接收范围保留 |
| 关闭隔空投送面板 | 恢复隐藏；通过原生枚举与恢复记录交叉确认 |
| 输入法切换隐藏 | 选择即时应用，托盘保留“输入法切换”；系统原生源消失 |
| 点击输入法切换 | 真实 AXMenu 与输入法、表情符号、虚拟键盘等原生菜单项出现，尺寸与屏幕位置有效；应用确认菜单已打开 |
| 关闭输入法菜单 | 原生源再次消失，记录为 hidden；输入菜单偏好文件只有 visible 字段变化 |
| 重启 | 两个系统入口重新收纳，分类保留；托盘共有 15 个入口，管理页无待处理项 |
| Clash Verge | 托盘默认打开主窗口，实机主窗口与应用日志均确认；未发送模拟右键，也不声称复制全部第三方右键行为 |

正常退出测试中，两项系统入口都恢复成功；另一个应用 Atoll 的原生应用恢复首次未完成，经应用内“重试恢复图标”后成功，活动恢复记录清空，再正常退出并重启。该现象的根因尚未确定，因此不能宣称所有第三方恢复都无须重试。
