# 可选原始图像状态修复（2026-11-16）

## 现场证据与根因

0.7.26（build 102）在本机已安装应用中持续显示“需要处理 / 部分图标图像尚未获取（6/21）”。此前验收确认了提示不再改变列表布局，但没有解决这条长期误报。

复查同一个已安装包时，托盘显示 20 个可用入口，其辅助功能说明全部标为“应用图标”；分类重试数与待处理数均为 0。既有运行日志记录 `captured=0 cached=15 requested=20 unavailable=20 failed=0`，表明这次读取没有可用独立窗口绑定，返回已有缓存，未发生截图执行失败。它不能证明所有系统窗口都无法采集，也不代表 20 个托盘入口不可用。

源码中的三条路径不一致：

1. `HiddenPanelIconButton.displayedImage` 优先选择应用图标，其次选择原始菜单栏图像，再显示名称。
2. `hiddenImageCoverage` 统计观测到的收起和始终隐藏来源，而不是本次显示的托盘入口。21 个统计来源与默认托盘 20 个入口不属于同一范围。
3. 原 `updateIconImageWarning` 仅比较原始截图缓存：21 个来源中有 15 个缓存，就生成 6/21 告警；`SettingsView.statusAttentionMessage` 再将其升级成全局“需要处理”。后台补采与托盘轮询也未排除已有应用图标的项目。

因此，缺少可选截图不等于缺少可用托盘图标。隐藏项目可能没有可确认的可见矩形或独立窗口；继续要求用户展开溢出区，不能作为正常使用托盘的前提。修复不放宽截图身份验证、不裁剪整屏来猜测图标，也不修改用户的分类来消除统计差额。

## 0.7.27（build 103）行为

- 删除全局图像缺失告警通道。截图缓存差额、离线记录、未启用可选屏幕录制均不会自动进入底部状态栏或“状态详情”。
- 在权限页保留“查看原始图像状态”按钮，主动点击才打开普通信息浮层。统计清楚说明原始图像是可选增强，托盘可以使用应用图标或名称。
- 后台补采只处理缺少应用图标且缺少原始缓存的显示条目；同一应用的重复来源不再分别补采。托盘所有条目已有应用图标时，不启动每 750 毫秒的截图轮询。
- 不跨检查携带旧的采集准备问题；图像统计也不再清除独立操作错误。分类、原生菜单操作及恢复失败仍按原有错误路径显示处理入口。
- 更正原始图像权限说明：已验证图像可以缓存在本机，不上传且不采集声音。

## 本地验证

`./scripts/check.sh --full` 通过 Python 110 项、Swift 核心 540 项、应用集成 189 项测试。Swift 使用 warnings-as-errors；检查日志未出现编译或 SwiftUI 警告。

本轮回归覆盖：

- 原始截图部分或全部缺失、离线记录及未授予屏幕录制不会变成全局错误。
- 真实操作错误在截图统计更新后仍保留。
- 新检查不会继续显示旧的采集准备失败。
- 已有应用图标时，无论原始缓存是否为空都无需后台补采。
- 多来源应用只为实际显示的来源请求回退图像；范围外条目不采集。
- 中英文图像诊断切换、固定状态栏及滚动位置回归继续通过。

日志与发布、安装凭据保存在忽略目录 `.local/release-0.7.27-20261116/`。模拟系统集成测试验证判定逻辑；安装后的真实菜单栏仍需单独验收。
